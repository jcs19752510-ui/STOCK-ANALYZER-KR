# 전 종목 준실시간 시세 스냅샷 설계 (REST 멀티종목 시세 순환 호출)

- 작성일: 2026-10-06 / 상태: **구성요소(모듈·모의 서버·시험·설계)만 완료, 앱 연결 안 함** / 관련: `06-realtime-review.md` §2(스크리닝 전 종목은 웹소켓 불가 → REST 순환)
- 한 줄 요약: 증권사 웹소켓은 한 연결에 구독 40건이라 전 종목(약 2,800) 틱 실시간이 불가능하다. 대신 **관심종목 멀티종목 시세**(한 번에 30종목)를 94번 순환 호출해 전 종목을 수 초~수십 초 주기로 갱신하는 "준실시간 스냅샷"을 메모리에 유지한다. **틱 단위 실시간이 아니다.**

## 1. 방식
| 항목 | 내용 |
|---|---|
| 호출 | `GET /uapi/domestic-stock/v1/quotations/intstock-multprice`, tr_id `FHKST11300006`, 파라미터 `FID_COND_MRKT_DIV_CODE_1..30`(`J`=KRX) + `FID_INPUT_ISCD_1..30`. 응답 행은 `output` |
| 구현 | `KisClient.multi_price(codes)`(최대 30개, 토큰·throttle·오류 처리는 기존 `_get` 재사용) → `normalize_multi_price(rows)` → `MarketSnapshotPoller`(asyncio) |
| 순환 | 종목 목록을 30개씩 묶어 차례로 호출. 호출 사이에 `min_interval`(+0~10% 지터)을 지킨다. 블로킹 호출은 `asyncio.to_thread` |
| 실패 처리 | 한 묶음이 실패해도 그 바퀴를 계속한다. 실패한 묶음은 **다음 바퀴에서 다시 시도**하고, 그 사이 그 묶음 종목은 이전 값을 유지한다(`fetched_at`으로 낡음 판별). 연속 실패 횟수에 따라 1·2·4…초(최대 60초) 지수 백오프를 다음 호출 앞에 건다(`RATE_LIMITED` 포함) |
| 저장 | 메모리만(DB·디스크 없음). 프로세스가 재시작되면 한 바퀴 돌 때까지 비어 있다 |
| 장 시간 | 기본: 평일 08:00~20:00 KST(통합시세 NXT 포함)만 연속 순환. 그 밖은 첫 바퀴(마감 값 채우기) 이후 `off_hours_cycle_interval`(기본 300초)마다 한 바퀴. 공휴일은 모르므로 휴일 장중에도 순환한다(달력 주입 가능: `is_market_open`) |
| 종목 목록 | `set_codes()`로 교체. 신규는 다음 바퀴부터 조회, 빠진 종목(상장폐지)의 값은 즉시 제거 |
| 지표 | `metrics()`: 호출 수, 오류 수, RATE_LIMITED 수, 누락 종목 수, 바퀴 수, 마지막 바퀴 소요 시간, **마지막 완주(전 묶음 성공) 시각**, 연속 오류, 마지막 오류 코드 |
| 값 규칙 | 현재가·전일대비·등락률·누적거래량·시가·고가·저가 중 하나라도 비었거나 숫자가 아니면 그 종목은 버린다(0으로 채우지 않음). 현재가 ≤ 0, 거래량 < 0, 종목코드가 6자 영숫자가 아니면 버린다. 부호(`prdy_vrss_sign` 1·2 상승, 4·5 하락)는 전일대비·등락률에 적용 |

## 2. 호출량 계산표 (2,800종목 = 94회/바퀴, 응답 지연 제외 이론값)
호출 한도(초당 건수)는 **공식 확인이 안 된 값**이라 아래는 가정별 계산이다. 한 바퀴 시간 = 94 ÷ 초당 호출 수.
| 가정 호출 한도 | 호출 간격 | 한 바퀴(2,800종목) | 1분당 호출 | 1시간당 호출 |
|---|---|---|---|---|
| 5건/초 | 0.20초 | 18.8초 | 300 | 18,000 |
| 8건/초 | 0.125초 | 11.8초 | 480 | 28,800 |
| 10건/초 | 0.10초 | 9.4초 | 600 | 36,000 |
| 20건/초 | 0.05초 | 4.7초 | 1,200 | 72,000 |
- 실제로는 응답 지연(왕복 시간)이 호출 간격에 더해질 수 있다. 호출을 순차로 하므로 응답이 0.1초 걸리면 20건/초 가정은 달성되지 않는다.
- 현재 `KisClient`는 자체 최소 간격 0.12초(≈8건/초)를 이미 두므로, 폴러 간격이 더 짧아도 실효 간격은 큰 쪽이다. 폴러 기본값은 보수적 가정인 `min_interval=0.2`(5건/초, 한 바퀴 약 19초).
- 종목 수 영향: 종목이 3,000개로 늘면 100회, 4,000개면 134회(5건/초 기준 26.8초).
- 코드의 계산 함수: `estimate_cycle_seconds(n_codes, calls_per_second)`, `calls_per_cycle(n_codes)`.

## 3. 한계와 위험
| 위험 | 내용 | 대응 |
|---|---|---|
| 호출 한도 미확인 | 한도를 넘으면 `RATE_LIMITED`(EGW00201 또는 HTTP 429). 계정 제재 여부 미확인 | `min_interval`을 설정으로 빼고 보수적 기본값. 스모크 시험에서 실제 한도를 측정한 뒤 조정. 백오프로 자동 후퇴 |
| 장 시작 직후 폭주 | 08:00·09:00에 첫 바퀴가 몰리고, 토큰 발급·여러 화면의 동시 요청과 겹침. 시가·고가·저가가 0인 값이 올 수 있음 | 폴러 시작을 장 시작 직전에 두고 첫 호출에 지터. 현재 정규화는 시가·고가·저가의 0을 값으로 받는다(장 시작 전 0 처리 정책은 실제 응답 확인 후 결정) |
| 종목 수 증가 | 신규 상장으로 바퀴 시간이 늘어남 | 종목 목록 교체로 반영. 지표의 바퀴 소요 시간 감시 |
| **앱키 공유 간섭** | 같은 앱키·같은 호출 한도를 종목 상세 화면의 REST(분봉·호가·체결)와 웹소켓 접속키 발급이 함께 쓴다. 순환 호출이 한도를 채우면 상세 화면 호출이 `RATE_LIMITED`를 받을 수 있음 | 한도의 일부(예: 70%)만 순환에 배정하는 공용 조절기가 필요(미구현, 다음 단계). 현재 `KisClient`의 throttle은 클라이언트 인스턴스 단위라, 인스턴스를 공유하지 않으면 합산 한도를 지키지 못한다 → **같은 `KisClient` 인스턴스를 공유**해야 함 |
| 낡은 값 | 묶음 실패·응답 누락 시 이전 값이 남는다 | `fetched_at` 확인, `last_full_cycle_at`으로 전체 신선도 판단. 소비 측은 일정 시간 이상 지난 값을 제외해야 함 |
| 프로세스 재시작 | 메모리만 사용 → 재시작 직후 비어 있음 | 의도된 설계. 소비 측에서 빈 스냅샷을 정상 상태로 처리 |
| 공휴일 | 달력을 모름 | 기본은 평일만 장중으로 간주. 휴장일 달력(`calendar`) 주입 예정 |
| 단일 이벤트 루프 | 폴러는 한 asyncio 루프에서만 쓴다(스레드 안전하지 않음) | API 서버 프로세스당 1개, 다중 워커 금지(앱키당 한 곳에서만 순환) |

## 4. 다음 단계 (이 작업에서는 하지 않음)
1. **연결**: 소유자 전용 모드에서 `MarketSnapshotPoller(make_kis_fetcher(kis_client), codes)`를 기동하고 종료 시 `stop()`. 종목 목록은 `stocks` 마스터(활성 종목)에서 주입, 라우터·화면은 별도 작업.
2. **스크리닝 장중 재계산**: 일봉 이력(DB) + 스냅샷의 오늘 시가·고가·저가·현재가·누적거래량으로 "진행 중인 오늘 봉"을 만들어 기존 `derivation` 순수 함수를 재사용. 비용 추정(미측정 가정): 2,800종목 × 지표 계산을 한 바퀴(9~19초)마다 다시 돌리면 호출 부하는 REST가 지배적이고, 계산은 순수 함수라 종목당 밀리초 단위로 보는 것이 합리적이나 **실측 필요**. 처음에는 "바퀴 완주 시각" 기준으로 1분마다 재계산하고, 결과 화면에 "마지막 완주 HH:MM:SS"와 "준실시간(수 초~수십 초 지연)"을 표시한다.
3. **호출 한도 공용 조절기**: 상세 화면 REST·접속키 발급·순환 호출이 한 토큰 버킷을 나눠 쓰고, 상세 화면이 우선하도록 한다.
4. **실측**: 장중에 스모크 시험으로 (a) 응답 필드명 확인 (b) 한 번에 30종목이 실제로 되는지 (c) 초당 한도 측정 (d) 장 시작 전 시가·고가·저가 값 확인.

## 5. 시험(실제 증권사 접속 없음)
`tests/unit/test_market_snapshot.py`: 30개 경계(0·1·29·30·31·60·2,800종목 → 94회), 클라이언트 파라미터·31개 거부·RATE_LIMITED 코드, 정규화(빈 값·비숫자·0 이하 가격 버림, 부호), 한도별(5/8/10/20건/초) 한 바퀴 주기(가짜 시계), 지터 하한, 실패한 묶음만 다음 바퀴 재시도(이전 값 유지), 지수 백오프·상한·복귀, 종목 목록 교체(조회 중 교체 포함), 시작/정지·재시작·긴 대기 즉시 중단·장 시간 밖 느린 순환, 모의 REST 서버 종단(70종목 + 빈 값 행, 31개 요청 오류).

## 6. 확인하지 못한 것
- **REST 호출 한도(초당 건수)**: 공식 수치 미확인. 위 표는 가정이다.
- 응답 필드명의 **실제 응답 대조**(앱키 없음) 및 샘플 파일 원문 직접 대조(도구가 요약 응답을 줌). `prdy_ctrt`가 부호 포함인지 절대값인지(코드는 둘 다 처리).
- 30종목 동시 조회 시 종목 중 일부가 잘못된 코드일 때 서버가 전체를 거절하는지 일부만 빼는지.
- `FID_COND_MRKT_DIV_CODE_n`에 NXT(`NX`)·통합(`UN`) 값을 쓸 때의 동작(현재 코드는 `J` 고정. 샘플은 `J`, `NX`를 언급).
- 장 시작 전·마감 후 시가·고가·저가·거래량 값의 형태(빈 값 또는 0).
- 앱키 공유 시 상세 화면 호출과의 실제 간섭 정도, 해외(Render) IP 접속 가능 여부, 약관상 순환 조회의 허용 범위.
- 휴장일 달력 연동(미구현).
