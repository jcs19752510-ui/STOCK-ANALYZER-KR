# 로그인 기능 설계서 (DEC-067, 승인 대기)

- 작성일: 2026-10-05
- 상태: **설계 검토 단계. 구현하지 않았다.** 아래 §9 승인 항목에 사용자가 동의한 뒤에만 구현한다.
- 요청(사용자): "회원 가입 없음. 내가 강제로 넣은 회원만 로그인해 조회할 수 있게. 로그인하면 로그인 가능한 사람들을 조회하는 메뉴."
- 사용자 선택(2026-10-05): ① 보호 수준 **A**(웹이 API를 대행, API는 웹의 비밀 토큰이 없으면 거부) ② 회원 정보는 **Neon 테이블 + 관리자 스크립트** ③ 회원 목록은 **로그인한 모든 회원이 아이디·이름만** 조회 ④ **운영(Render) 사이트에만** 적용(로컬은 현재처럼 로그인 없음).

## 1. 확인한 현재 구조(코드 근거)와 설계에 미치는 영향

| 사실 | 영향 |
|---|---|
| API의 `X-Internal-Token`은 접근 통제가 아니라 **분당 호출 한도 버킷을 나누는 용도**(`services/public_api/rate_limit.py`) | 웹 화면에만 로그인을 붙이면 API 주소로 바로 조회할 수 있다 → **API가 토큰을 강제**해야 한다 |
| 브라우저가 API를 **직접** 호출하는 코드가 5곳(`screenApi`, `patternApi`, `stockSearchApi`, `useLazyApi`, `useQuotes`) | 이 5곳을 **웹 서버 경유**로 바꿔야 한다 |
| 서버 컴포넌트(홈·종목 상세)는 이미 웹 서버가 토큰을 붙여 API를 호출 | 변경 최소, 단 로그인 세션 확인이 선행돼야 한다 |
| 웹(`stock-analyzer-web-*.onrender.com`)과 API(`stock-analyzer-api-*.onrender.com`)는 서로 다른 서브도메인 | API가 심은 쿠키는 웹에서 차단될 수 있다(**확정 못 함**) → **세션 쿠키는 웹 서버가 발급** |
| `api_service`는 읽기 전용, `public_serving`만 접근 | 회원 테이블·잠금 갱신을 위해 **별도 DB 계정**이 필요하다(최소 권한) |
| 웹 서버에는 DB 비밀번호가 없다 | 계정 확인은 웹 서버가 **API의 내부 전용 경로**를 호출해 처리 |
| 현재 API 호출 한도는 토큰이 있는 요청을 **하나의 내부 버킷**으로 센다 | 대행 구조에서는 모든 회원이 한 버킷을 공유 → **회원 id로 버킷을 나눈다** |
| 내부 토큰 값이 대화에 노출된 이력이 있다 | 이 토큰이 **실제 출입문**이 되므로 **구현 전에 반드시 교체**(선행 조건) |

## 2. 구조

```
브라우저 ── 세션 쿠키(웹 도메인) ──> 웹 서버(Next.js)
                                       │ ① 요청마다 쿠키 검증(proxy)
                                       │ ② /bff/* 는 허용 경로만, 조회(GET)만 API로 전달 (X-Internal-Token + 회원 id)
                                       ▼
                                    API 서버(FastAPI)
                                       │ /api/v1/* : 토큰 없으면 거부 (/api/v1/live 만 예외)
                                       │ /internal/auth/* : 토큰 필수, 브라우저 호출 불가
                                       ▼
                                    Neon (public_serving: 읽기 전용 / auth: 별도 계정)
```

- **브라우저는 웹 도메인만 호출**한다. API 주소를 알아도 토큰 없이는 데이터가 나오지 않는다.
- 로컬 개발은 스위치가 꺼져 있어(`AUTH_REQUIRED`, `PUBLIC_API_REQUIRE_INTERNAL_TOKEN`) 지금처럼 동작한다.

## 3. 데이터 모델 (마이그레이션 0015, 새 스키마 `auth`)

`auth.app_users`
| 컬럼 | 설명 |
|---|---|
| `user_id` uuid PK | |
| `username` text unique(대소문자 무시) | 로그인 아이디 |
| `display_name` text | 화면 표시 이름 |
| `password_hash` text | **argon2id** 해시(원문 저장 안 함) |
| `is_active` bool | 비활성이면 로그인·조회 불가 |
| `failed_attempts` int, `locked_until` timestamptz | 로그인 실패 잠금 |
| `last_login_at`, `created_at`, `updated_at` | (회원 목록에는 **노출하지 않음**) |

`auth.login_audit`: 시각, `user_id`(없을 수 있음), 시도한 아이디(길이 제한), 결과(성공/실패/잠김), 접속 IP(마지막 옥텟 마스킹 여부는 §9에서 승인). 비밀번호는 기록하지 않는다.

DB 계정(최소 권한)
- `auth_service`: `auth.app_users` SELECT, UPDATE(`failed_attempts`, `locked_until`, `last_login_at`)만, `auth.login_audit` INSERT만. `public_serving`·`raw_internal` 접근 없음.
- `api_service`: `auth` 스키마 접근 **없음**(데이터 조회 계정과 분리).
- 회원 추가·변경은 관리자 스크립트가 `migrator`(또는 소유자) 연결로만 수행.

## 4. 흐름

**로그인**: `/login` → `POST /auth/login`(웹 서버) → 웹 서버가 `POST /internal/auth/verify`(토큰 필수) 호출 → API가 `auth_service`로 계정 확인(argon2id 검증, 없는 아이디도 **같은 시간·같은 오류 문구**) → 성공 시 웹 서버가 **서명된 세션 쿠키** 발급(`__Host-` 접두어, HttpOnly, Secure, SameSite=Lax, 도메인 없음, 절대 만료 기본 8시간) → 원래 보려던 화면으로(**같은 사이트 내부 경로만 허용**, 열린 리다이렉트 방지).

**조회**: `proxy`가 모든 경로(`/login`, 정적 파일 제외)에서 쿠키를 검증, 없으면 `/login`으로. 서버 컴포넌트와 `/bff/*`는 로그인 회원만. 비활성화된 회원은 **최대 5분 안에** 차단(상태 재확인 주기).

**잠금**: 같은 아이디 5회 연속 실패 시 15분 잠금(반복 시 증가), 아이디·IP 단위 호출 한도 병행. 성공하면 실패 횟수 초기화.

**로그아웃**: 쿠키 삭제(서버 측 세션 저장소는 없음 — §7 트레이드오프).

**회원 목록**: 머리글 메뉴 "회원 목록"(로그인 시에만 보임) → `/members` → 웹 서버가 `GET /internal/members` 호출 → **활성 회원의 아이디·이름만**. 이름은 화면에서 이스케이프(스크립트 삽입 방지).

## 5. 관리자 스크립트 `scripts/manage_users.py` (PC에서 실행, 비밀번호는 인자로 받지 않고 숨김 입력)

`add <아이디> --name <이름>`, `set-password <아이디>`, `disable`/`enable <아이디>`, `delete <아이디>`, `list`. 회원 가입·비밀번호 찾기·본인 비밀번호 변경 화면은 **없다**(요청대로). 비밀번호 정책 기본값: 최소 12자, 아이디와 같지 않음, 흔한 약한 비밀번호 목록 거부(§9 승인).

## 7. 보안 검토와 알려진 트레이드오프

| 위협 | 대응 |
|---|---|
| 로그인 우회로 API 직접 호출 | API가 토큰 강제, `/docs` 비노출, 허용 경로만 대행 |
| 무차별 대입·자격 증명 대입 | 아이디별 잠금, IP·아이디 호출 한도, argon2id, 로그인 지연의 일관화 |
| 아이디 존재 여부 추측 | 같은 문구·같은 처리 시간(없는 아이디도 더미 해시 비교) |
| 세션 탈취 | HttpOnly+Secure+SameSite, `__Host-` 접두어, 인증 화면 `Cache-Control: no-store`, 검색엔진 색인 금지 |
| CSRF | 상태 변경은 로그인·로그아웃 POST뿐이며 SameSite=Lax + `Origin` 검사. 대행 경로는 GET 전용 |
| 열린 리다이렉트 | 로그인 후 이동 경로는 같은 사이트의 `/`로 시작하는 경로만 |
| 비밀 노출 | 비밀번호·토큰·해시는 로그에 남기지 않는다. 내부 토큰은 **구현 전 교체** |
| 회원 목록의 개인정보 | 아이디·이름만. 이메일·마지막 접속 시각·해시는 노출하지 않음 |
| **서버 측 세션 저장소 없음(서명된 쿠키)** | **로그아웃·비활성화가 즉시 전체 무효화가 아니다.** 만료 8시간, 상태 재확인 5분으로 완화. 즉시 폐기가 필요하면 세션 테이블 방식으로 바꿔야 하며 DB 조회가 늘고 깨우기 지연이 커진다 → 승인 항목 |
| 무료 호스팅 | 로그인 확인이 API 깨우기를 유발할 수 있다. 로그인 화면은 정적, 확인 중 대기 팝업 동작은 유지. 인증 실패 화면은 일반 오류와 구분 |

## 8. 시험 계획(구현 시 결과서에 전부 기록)

- 단위: 해시·검증, 잠금 계산, 세션 서명·만료·변조, 경로 허용 목록, 리다이렉트 검사, 정책 검사
- API: 토큰 없음/틀림 → 거부(`/api/v1/live` 제외 전 경로), 대행 전용 경로를 브라우저가 못 부름, 회원 id별 호출 한도
- DB(실제 PostgreSQL): 마이그레이션 0015 적용·되돌리기, `auth_service`·`api_service` 권한 경계(다른 스키마 접근 거부, 해시 열 읽기 거부)
- 웹/브라우저(Playwright): 비로그인 → 모든 화면 로그인으로 이동, 로그인 성공/실패/잠금/로그아웃, 회원 목록(이름 이스케이프), 쿠키 속성, 세션 만료, 직접 API 호출 차단, 열린 리다이렉트·CSRF, 접근성(axe), 360px·1280px
- 회귀: 기존 프런트 88건, 브라우저 시험, 백엔드 단위·통합 전체
- 보안 점검(09 단계 방식): 인증·세션·권한·비밀 노출·의존성

## 9. 승인이 필요한 항목(기본값을 적었다. 바꾸고 싶은 것만 알려 주면 된다)

1. 세션: **절대 만료 8시간 + 5분마다 상태 재확인**(서명 쿠키). 즉시 폐기가 필요하면 세션 테이블 방식.
2. 비밀번호 정책: **최소 12자**, 아이디와 동일 금지, 약한 비밀번호 거부.
3. 잠금: **5회 연속 실패 → 15분**(반복 시 증가).
4. 로그인 기록 IP: **마지막 옥텟 마스킹** 저장, 보관 90일.
5. **선행 조건**: 내부 토큰(`PUBLIC_API_INTERNAL_TOKEN`) 새 값으로 교체(Render 두 서비스), 같은 시점에 Neon 소유자·앱 계정 비밀번호 교체(공개 전 항목과 통합).
6. 구현 순서와 중간 점검: U1 DB·관리자 스크립트 → U2 API → U3 웹 로그인·대행 → U4 회원 목록 → U5 보안 점검·E2E → U6 문서·운영 반영. **운영 반영은 사용자가 Render에서 진행**하며, 반영 순서는 API(스위치 끔) → 웹 → 스위치 켬.
7. 롤백: 웹 `AUTH_REQUIRED=false`, API `PUBLIC_API_REQUIRE_INTERNAL_TOKEN=false`로 재배포하면 로그인 없는 현재 상태로 복귀.

## 10. 미확인 사항

- 웹·API 서브도메인 간 쿠키 차단 여부(설계는 차단을 가정하고 웹 쿠키로 회피)
- Render 무료 서버에서 argon2id 검증 시간과 메모리(시험으로 확정)
- 같은 회원이 여러 탭·기기에서 쓸 때 상태 재확인과 호출 한도의 상호작용
- 대행 경유 후 응답 지연 증가폭(측정 예정)
