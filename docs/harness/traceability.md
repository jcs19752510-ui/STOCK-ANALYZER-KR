> 이후 단계에서 새 ID를 임의로 추가하지 않는다. 새 요구사항이 필요하면 규칙 A에 따라 질문하거나 규칙 F(피드백 루프)로 2단계 산출물을 수정한다.

> **6단계 v3 재검증 갱신(실제 PostgreSQL 확보에 따른 AC-3/AC-5 확정 검증)**: 코디네이터가 로컬 Docker에 실제 PostgreSQL 16(컨테이너 `stock-screener-db`, 역할 `migrator`/`batch_worker`/`api_service`)을 준비함에 따라, 6단계(`docs/harness/units/unit-01-test.md` v3)가 v2까지 "미검증"으로 남겨뒀던 AC-3 불릿4(CLI 실 upsert)·AC-5(실 마이그레이션 적용/롤백)를 실제 DB로 **확정 PASS** 처리했다(마이그레이션 적용/롤백, 730건 upsert, 재실행 idempotency 전부 실제 쿼리로 확인). 이 과정에서 코드 자체의 신규 결함 2건을 발견했다: **DEF-003(Medium, Open)** — 마이그레이션이 `reference` 스키마에 대해 GRANT 문을 전혀 실행하지 않아, 역할이 분리된 프로덕션 환경에서는 GRANT 없이 CLI 실행이 100% 실패함(재현 확인). **DEF-004(Low, Open)** — `scripts/load_calendar.py`의 upsert가 `updated_at`을 갱신하지 않아 감사 추적성이 저하됨(재현 확인). 두 결함 모두 Fake 기반 단위테스트로는 발견할 수 없었던 실제 인프라 전용 결함이다. `api_service`의 `raw_internal` 접근 거부는 UNIT-02 산출물이 아직 없어 대역(proxy) 스키마로만 보조 검증했고(원리 확인, 실제 코드 검증 아님), UNIT-02 완료 후 재검증이 필요하다. 종합 판정은 **CONDITIONAL PASS 유지**(조건이 "Postgres 미검증"에서 "DEF-003 Open 해결"로 전환됨) — DEF-003이 Fixed 되기 전에는 9~11단계(보안검증/배포테스트/배포) 진입 불가로 명시. 상세 근거는 `docs/harness/units/unit-01-test.md`(v3) §8/최종 판정 요약 참조.

## 작성 규칙
- REQ-ID는 2단계에서 기획서의 기능 범위(In-Scope) 항목마다 하나씩 부여한다. 이후 단계에서 새 ID를 임의로 추가하지 않고, 새 요구사항이 필요하면 규칙 A에 따라 질문하거나 규칙 F(피드백 루프)로 상위 단계를 수정한다.
- Out-of-Scope로 명시된 항목은 매트릭스에 포함하되 상태를 "Out-of-Scope(사유)"로 표기해, 나중에 "빠뜨린 것"과 "의도적으로 뺀 것"을 구분할 수 있게 한다.
- **REQ-005, REQ-006, REQ-007, REQ-008, REQ-009, REQ-010, REQ-012는 규칙 I(규제 민감 도메인 대응)에 따라 등록된 항목이다.** 9단계 보안/규제 검증에서 이 항목들의 실제 구현/화면 반영 여부를 별도로 확인하고, 미반영 시 Critical 결함과 동일하게 취급한다(규칙 I-3).
- **REQ-022도 규칙 I(규제 민감 도메인 대응)에 따라 등록된 항목이나, 성격이 다르다.** 이는 화면/기능 구현이 아니라 **12단계(배포) 착수 전 별도 확인 절차(게이트)**이므로 5~8단계의 구현/테스트 사이클과 무관하게 존재하며, 8단계 커버리지 체크 시에도 "구현 상태"가 아니라 "12단계 배포 승인 체크리스트에서 확인되었는가"로 판정한다. 8단계에서 이 항목이 Out-of-Scope나 누락으로 처리되어서는 안 된다 — 배포를 막는 실질적 요구사항이다.
- 8단계에서 이 매트릭스를 검토해 커버리지 100%를 확인하지 못하면 PASS 판정할 수 없다(REQ-022 포함).
- **REQ-026/REQ-027(v8 신규)도 REQ-022/024/025와 동일한 성격의 게이트다** — 09단계(보안검증)가 발견한 설계-구현 불일치(DEF-SEC-01/02)에 대응해 등록됐으며, 대상 단계는 REQ-025와 동일하게 10단계(배포테스트) 착수 게이트다. 세 REQ(025/026/027) 모두 근본 원인이 동일 산출물(UNIT-01의 `services/public_api` 공용 기반)로 귀속되어 `decisions.md` DEC-027에 따라 한 번의 5→6→8→9단계 재작업 사이클로 함께 처리된다.
- **REQ-024(v6 신규)도 REQ-022와 동일한 성격의 게이트다** — 다만 대상 단계가 다르다(REQ-022는 12단계 배포 승인 게이트, REQ-024는 10단계 배포테스트 착수 게이트). 07단계(stock-metrics 통합테스트)가 CONDITIONAL PASS로 8~9단계 진행 자체는 막지 않았으므로, 8·9단계 커버리지 체크에서 REQ-024를 "Out-of-Scope/누락"으로 처리하지 말고 "10단계 착수 전 확인 필요"로 표시된 상태 그대로 통과시킨다. 10단계 착수 직전에는 반드시 이 게이트의 Pass 여부를 확인해야 하며, 확인 없이 10단계로 넘어가는 것은 규칙 D(단계 게이트) 위반이다. 근거: `decisions.md` DEC-024. **(screener 통합테스트 권고 반영)** 이 게이트는 REQ-002/REQ-011뿐 아니라 `derived_metrics_daily`를 소비하는 REQ-003(screener)·REQ-004(market-summary)에도 동일하게 적용된다 — 원인(Ingestion→Derivation 배치 체인 실행 이력 없음)이 테이블 자체에 있어 이를 소비하는 모든 기능이 동일 리스크를 공유하기 때문이다.
