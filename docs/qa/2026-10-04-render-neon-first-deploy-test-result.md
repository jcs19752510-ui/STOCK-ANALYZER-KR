# Render + Neon 첫 배포 내부시험 결과서 (DEC-063, 비공개 상태)

- 작성일: 2026-10-04
- 시험 방식: 사용자 PC·Render·Neon 콘솔에서 사용자가 실행한 명령과 화면(캡처·로그)을 근거로 기록. 이 문서를 쓴 세션(샌드박스)은 Render·Neon·사용자 PC에 직접 접속하지 않았고, 운영 배포를 대신 실행하지 않았다.
- 대상 커밋: `5ec9473` (PROD_SCH). Render Blueprint `STOCK-ANALYZER-KR`.
- **상태: 비공개.** 주소를 외부에 알리지 않았고, Render 프록시 대역 확인(§7 F-5)이 끝나기 전에는 공개하지 않는다.

## 4. 화면 비교: 로컬(localhost:4000) vs 운영(Render)

비교 대상: 홈(`/`), 급등 전 압축주(`/screener/pattern`). 사용자 지적은 "CSS가 맞지 않는 것 같다"였다.

### 4-1. CSS 검토

캡처에서 글꼴, 색, 버튼·체크박스·표 레이아웃, 배지, 배너 모양은 **로컬과 운영이 동일**했다. **CSS 결함은 발견하지 못했다.** 사용자가 느낀 "다름"은 아래 4건에서 나온다. (제약: 캡처 2장 비교이며, 두 캡처의 브라우저 폭이 달라 픽셀 단위 비교가 아니다. 모바일 폭·다른 브라우저는 시험하지 않았다.)

### 4-4. 종목 상세 화면의 탭 차이 (F-7) — 사용자 결정 대기

- 증거: [화면] 로컬 `/stocks/068760`에는 탭 7개(호가·차트·체결·일자별 시세·실적·투자자·조건 체크), 운영에는 3개(실적·투자자·조건 체크). 로컬에는 헤더의 현재가·등락, 차트(캔들·이동평균·거래량·MACD·매물대·차트 요약)가 보이고 운영에는 없다.
- 원인(코드 확인, `StockDetailTabs.tsx`, `app/stocks/[code]/page.tsx`, `priceExposure.ts`, `localIntraday.ts`): **오류가 아니라 두 개의 스위치가 4개 탭을 숨기는 설계 동작이다.**

| 숨겨진 탭 | 숨기는 조건 | 운영 값 |
|---|---|---|
| 차트, 일자별 시세 (+헤더의 현재가·등락) | 프런트 `NEXT_PUBLIC_PRICE_EXPOSURE_ENABLED`가 정확히 `"false"`이면 숨김(빌드 때 확정) + API `PUBLIC_API_PRICE_EXPOSURE_ENABLED=false`이면 시세 API가 404 | 둘 다 `false` (`render.yaml`) |
| 호가, 체결 (분·틱 포함) | ① `NEXT_PUBLIC_LOCAL_INTRADAY_ENABLED=true`, ② 시세 공개 스위치 켜짐, ③ 브라우저 주소가 사설망·localhost일 때만 표시. API도 허용 IP·환경변수로 한 번 더 막음 | 해당 없음 (공개 주소에서는 항상 숨김) |

- 배경 결정: DEC-048(시세 원값 공개 스위치, 법률 검토 REQ-022 전에는 숨김), DEC-050(기본값을 켜짐으로 환원하되 **외부 공개 배포 직전에는 법률 검토 결과에 따라 두 값을 `false`로 두는 것을 체크리스트에 명시, 사용자 책임·결정**), DEC-052(증권사 호가·체결·분·틱은 개인 로컬 모드 전용, **외부 공개 배포에서는 끄는 것이 전제**).
- 이 배포에서 두 값을 `false`로 둔 것은 DEC-048/050의 안전 기본값을 따른 것이며, 화면에서 무엇이 사라지는지를 사용자에게 사전에 충분히 알리지 못했다(DEC-050에서 이미 한 번 지적받은 사안과 같은 유형). 이 문서가 그 설명이다.
- 판정: **코드·CSS 결함 아님.** 운영에서 호가·체결(및 분·틱)은 **어떤 설정으로도** 공개 화면에 나오지 않는다(설계상 사설 주소 전용). 차트·일자별 시세는 스위치로 켤 수 있다.
- **결정 필요(사용자 책임):** 공개 서비스에서 차트·일자별 시세·현재가를 보여 줄지.

| 선택 | 결과 | 비고 |
|---|---|---|
| A. 현행 유지(숨김) — 권장 | 운영은 가공 지표·실적·투자자(준비 중)·조건 체크만 | 공공데이터포털 약관이 일봉 원값(시가·고가·저가·종가·거래량)의 제3자 제공·재배포를 금지하므로 법률 검토(REQ-022) 전의 안전한 상태 |
| B. 공개(켬) | 차트·일자별 시세·현재가·등락 표시 | 두 값을 `true`로 바꾸고 **웹을 재빌드해야** 반영됨(빌드 시점 값). 약관 위반 위험은 사용자 책임. 켜기 전에 법률 검토를 권장 |

- **결정: B(공개) 선택(사용자, 2026-10-04).** DEC-064로 기록했다.

### 4-5. 잠든 뒤 첫 접속의 "일시적인 오류" 화면 (F-8) — 선택지 A 구현·시험 완료, 운영 반영 대기

- 증거: [화면] 한동안 접속이 없다가 운영 홈(`stock-analyzer-web-q7cx.onrender.com`)을 열면 "일시적인 오류가 발생했습니다 / 다시 시도" 화면이 나옴. 사용자 질문: "서버를 띄우고 있다고 알리는 상태창은 구현이 안 된 것인가".
- **답: 구현은 되어 있으나 적용 범위가 좁고, 이 화면은 그 범위 밖이다.** 이 한계는 2026-10-03 결과서(미해결 한계 2)에 적어 두었으나, 운영 절차서에는 "화면에 안내가 뜹니다"라고만 적어 **범위를 과장했다.** 절차서를 정정했다(`render-neon-guide.md` 한계 항목).

| 상황 | "깨우는 중" 안내 | 근거 |
|---|---|---|
| 브라우저가 API를 부르는 요청이 4.5초 넘게 걸림(스크리닝 결과, 종목 탭, 검색 등) | **표시됨** | [코드] `ApiWakeNotice`(클라이언트 컴포넌트) + `apiWake.ts`가 브라우저의 `fetch`만 감시 |
| 웹 서비스 자체가 잠든 첫 접속 | **표시 불가**(웹이 아직 안 떠서 우리 코드가 실행되지 않음). Render가 대기시키는 구간 | [코드][절차서] |
| 홈·종목 상세처럼 **서버가 API를 부르는 화면**(서버 컴포넌트) | **표시 안 됨.** 이 화면들의 서버 측 호출(`fetchMarketSummary` 등)에는 대기 안내가 없고, 호출이 실패하거나 서버가 오류 응답을 주면 즉시 `NETWORK_ERROR`/`UNKNOWN_ERROR`로 처리해 "일시적인 오류" 화면을 보여 줌 | [코드] `marketSummary.ts`, `errorMapping.ts`, copy `networkTitle` |

- 완화 장치(이미 있음): 웹이 시작될 때 API의 `/api/v1/live`를 한 번 불러 API를 같이 깨운다(`instrumentation.ts`, 응답을 기다리지 않음).
- **오류 화면의 직접 원인은 확정하지 못했다(미확인).** 후보: ① 첫 요청이 API가 깨어나는 도중 실패, ② API는 깨어났으나 Neon(5분 유휴 시 정지)이 깨어나는 시간이 API의 연결 제한 10초·요청 제한 15초를 넘겨 오류 응답. 확정하려면 **오류가 난 시각의 API 서비스 Logs**와 "다시 시도"를 눌렀을 때 정상으로 바뀌는지가 필요하다. 사용자에게 요청함.
- 무료 요금제의 구조적 한계다(15분 유휴 시 서버 정지, 깨우는 데 약 1분). **상시 깨워 두는 방법(주기적 호출)은 권장하지 않는다:** 무료 시간 한도(Render 서비스 가동 시간, Neon 컴퓨트 100시간)를 넘길 가능성이 크다. 단 현재 Render 무료 정책의 정확한 시간 한도는 직접 확인하지 못했다.

개선 선택지(결정 필요, 결정 전에는 코드 변경 없음):

| 선택 | 내용 | 효과 | 비고 |
|---|---|---|---|
| A. 서버 호출 화면에 재시도·대기 안내 추가 (권장) | 홈·종목 상세 등 서버 컴포넌트에 ① 즉시 보이는 "서버를 깨우는 중" 로딩 화면(`loading.tsx`) ② 서버 측 호출의 짧은 재시도(깨어나는 동안 실패하면 몇 번 다시 시도) | 첫 방문자가 빈 화면·오류 대신 안내를 보고 잠시 뒤 정상 화면을 봄 | 코드 변경(프런트 + 시험 추가). 웹이 잠든 첫 구간은 여전히 불가 |
| B. 안내 문구만 오류 화면에 추가 | 오류 화면에 "잠들었다 깨는 중일 수 있습니다. 1분 뒤 다시 시도" | 가장 작은 변경 | 사용자가 직접 다시 시도해야 함 |

**시험 방식의 한계·미확인**
- 가짜 API로 만든 실패 상황이다. **실제 Render·Neon에서 잠든 뒤 첫 접속이 어떻게 보이는지는 직접 확인하지 못했다.** 사용자가 운영 반영 후 15분 이상 쉬었다가 접속해 확인해야 한다.
- 웹 서비스 자체가 잠든 첫 구간(Render 대기 화면)은 이 변경으로 해결되지 않는다.
- Render의 프록시가 스트리밍 응답(로딩 화면 먼저, 데이터 나중)을 중간에 모아서 늦게 내보내는지는 확인하지 못했다. 그렇다면 로딩 화면이 늦게 보일 수 있다.

### 4-6. 운영에도 호가·체결(및 분·틱·투자자 실데이터) 공개 — 검토 (F-9) — 사용자 결정 대기

- 사용자 질문: 로컬과 같이 모두 공개(선택지 3)할 때, **매수·매도 같은 거래를 하지 않으면 상관없는가.** 의도: "정보를 모두 직접 확인하고 싶다."
- 방법: 코드 확인(`services/public_api/intraday/*`, `api/local_intraday.py`, `frontend/src/lib/localIntraday.ts`·`privateHost.ts`), 기존 문서(`docs/stock-detail/04-intraday-options.md`, DEC-052), 웹 검색. **KIS(한국투자증권) 공식 약관 원문은 이번에도 열람하지 못했다**(검색 결과에 공식 약관이 나오지 않음). 아래 "약관·계약" 항목은 확인된 사실이 아니라 위험 판단이다.

**1) "거래를 하지 않으면 상관없는가" — 부분적으로만 그렇다**

| 쟁점 | 확인된 사실 | 판단 |
|---|---|---|
| 이 앱이 주문을 낼 수 있는가 | [코드] 호출하는 KIS 엔드포인트는 시세 조회 6개뿐(토큰, 당일·과거 분봉, 호가, 체결 2종). 주문·계좌 API는 호출하지 않는다고 `kis_client.py`에 명시. 계좌번호(CANO 등) 설정 항목도 코드에 없다 | **앱 코드만 보면 매매는 일어나지 않는다**(코드 확인) |
| 앱키가 새면 거래 위험이 있는가 | 앱키는 **실전 계좌에 연동된 키**다. 키만으로 주문이 가능한지(계좌번호·추가 인증 필요 여부)는 **확인하지 못했다** | **확인 전까지 "거래 가능한 키"로 취급**해야 한다. 공개 서버에 두면 유출 위험이 커진다 |
| 거래 여부와 관계없는 쟁점 | 호가·체결은 거래소(KRX)의 실시간 시세다. 불특정 다수에게 보여 주는 것은 "재배포"이며, 그것이 문제가 되는 것은 **거래 여부와 무관**하다. 기존 검토(DEC-052)는 법인이 시세를 자사 화면에 쓰려면 거래소(코스콤) **정보이용계약**이 필요하다는 안내를 근거로 들었다(원문 미열람) | **"매매하지 않으니 괜찮다"는 보장은 할 수 없다.** 법률 검토 사안(REQ-022와 같은 종류) |
| 개인 이용 표시 | 요청 헤더에 `custtype=P`(개인)를 쓴다 | 공개 서비스는 개인 이용 전제와 어긋날 수 있음(약관 미확인) |

**2) 공개하려면 기술적으로 막히거나 깨지는 곳(코드로 확인)**

| 항목 | 내용 |
|---|---|
| 접근 통제 4중 | 스위치, 허용 IP(기본 loopback), **프록시 헤더(`X-Forwarded-For` 등)가 있으면 거부**, `Host`가 사설 주소가 아니면 거부. Render 같은 공개 호스팅은 항상 프록시 헤더가 붙으므로 **설계상 작동하지 않는다.** 켜려면 이 통제를 풀어야 하고, 그 순간 방문자 누구나 호출할 수 있다 |
| 프런트 | 사설 주소(localhost, 10.x, 192.168.x, 172.16~31.x)에서만 탭을 보인다. 공개 도메인에서는 숨겨진다 |
| 토큰 캐시 | KIS 토큰은 6시간에 1회만 재발급할 수 있고(문서 기준), 코드는 토큰을 **로컬 파일**(`.local/kis_token.json`)에 캐시한다. Render 무료 서버는 쉬었다 깨면 재시작되어 파일이 사라질 수 있다 → 깨어날 때마다 재발급을 시도하고 제한에 걸릴 수 있다(**추정, 미시험**) |
| 호출 한도 | 모든 방문자가 한 개 앱키의 호출 한도를 함께 쓴다. 공식 한도 수치는 확인하지 못했다 |
| 투자자 탭 | 로컬의 투자자 실데이터도 같은 KIS 경로(개인 로컬 모드)다. 운영은 "준비 중" |

**3) 사용자 의도에 맞는 대안(권장 방향)**

의도가 "내가 직접 모든 정보를 보는 것"이면, **불특정 다수에게 공개할 필요가 없다.** 아래는 모두 **사용자 본인만 접속**하는 방식이다. 어떤 것도 이번 변경에 포함하지 않았고, 선택·설계·보안 검토 후에만 진행한다.

| 방식 | 내용 | 비고 |
|---|---|---|
| P1. 내 PC 로컬 모드(현행) | 집 PC에서 `localhost`로 7개 탭 모두 사용 | 이미 가능. 다른 기기에서는 같은 사설망 주소로 가능(user-action-guide 참고) |
| P2. 내 PC에 외부에서 나만 접속 | 개인 VPN·터널로 집 PC에 접속. 앱키는 PC에만 둔다 | 현재 사설 주소 판정 규칙이 VPN 대역(예: 100.x)을 포함하지 않아 **규칙 조정이 필요할 수 있음**(미확인). 터널은 프록시 헤더를 붙일 수 있어 통제 3번과 충돌할 수 있음(미확인). PC가 켜져 있어야 함 |
| P3. 로그인이 있는 비공개 서버 | 접속에 로그인이 필요한 서버에 앱키를 두고 나만 사용 | **로그인 기능이 현재 없다**(신규 개발+보안 검토). 서버에 앱키가 놓이므로 유출 위험 관리 필요. VPS 경로(`deploy/`)와 함께 검토 |
| 공개 | 불특정 다수에게 실데이터 공개 | **비권장.** 정보이용계약·앱키 관리·호출 제한·토큰 캐시 설계가 먼저 |

- 이 검토에서 **변경한 코드·설정은 없다.** 운영의 호가·체결 탭은 계속 숨겨져 있다.

### 4-7. 투자자 탭 화면 차이 두 건 (F-10, F-11) — 원인 확인 대기

사용자 보고(2026-10-05 00:01~00:02, 같은 종목 068760의 투자자 탭): ① 로컬: "개인 로컬 모드가 꺼져 있습니다. API 서버의 LOCAL_INTRADAY_ENABLED 설정을 확인하세요." 어제까지는 정상. ② 운영: "투자자별 수급은 준비 중입니다". 어제까지는 정상이었다고 함.

**F-11 운영의 "준비 중" — 설계된 동작(코드 확인)**

- `StockDetailTabs.tsx`: 투자자 탭은 `localMode`(개인 로컬 모드)일 때만 실데이터(`InvestorPanel`)를 그리고, 아니면 `investorPendingTitle/Body`("준비 중")를 보인다. `localMode`는 `NEXT_PUBLIC_LOCAL_INTRADAY_ENABLED=true`, 시세 공개 켜짐, **브라우저 주소가 사설망**일 때만 참이다(`localIntraday.ts`, `privateHost.ts`). 운영 주소(`*.onrender.com`)는 사설 주소가 아니므로 **항상 거짓**이다.
- 이 문구와 분기는 DEC-049/054에서 정한 것이며, 이번 세션에서 이 부분을 바꾼 커밋은 없다(투자자 탭 코드·문구의 마지막 변경은 이전 커밋).
- 따라서 운영에서 투자자 실데이터가 표시되는 경로는 코드에 없다. "어제까지 떴다"는 기억과 달라, **어제 본 화면이 로컬 화면이었는지 사용자 확인이 필요**하다(제가 확인하지 못한 경로가 있다면 알려 주세요). 판정: **결함 아님**.

**F-10 로컬의 "개인 로컬 모드가 꺼져 있습니다" — 원인 확정 못 함, 후보와 확인 방법**

- 화면 문구는 API가 `404 FEATURE_DISABLED`를 돌려줬을 때 나온다. API는 아래 4개 중 **하나라도** 어긋나면 같은 응답을 준다(존재를 드러내지 않으려는 설계라 어느 것인지 응답으로는 구분되지 않음): ① `LOCAL_INTRADAY_ENABLED=true` ② 요청 IP가 허용 목록(기본 127.0.0.1, ::1) ③ 프록시 헤더(`X-Forwarded-For` 등) 없음 ④ `Host`가 localhost·사설 주소.
- **가장 유력한 후보(미확정): API가 `.env`의 로컬 모드 변수 없이 다시 시작됨.** 이 API는 `.env`를 스스로 읽지 않는다. `scripts/start_local_api.ps1`이 필요한 키(`LOCAL_INTRADAY_ENABLED`, `KIS_APP_KEY`, `KIS_APP_SECRET` 포함)를 환경변수로 올려 기동하며, 다른 방법으로 기동하거나 목록에서 빠지면 바로 이 문구가 나온다(`로컬서버-접속방법.md`에도 명시). 어제와 달라진 점이 "API 재시작"이라면 설명이 된다.
- 다른 후보: `.env`의 값이 비었거나 주석 처리됨, 프록시 헤더를 붙이는 경로로 접속, 허용 IP 설정 변경.
- 이번 세션의 변경(프런트 재시도·로딩 화면, `render.yaml`, 문서)은 API의 개인 로컬 모드 코드와 `.env`를 건드리지 않았다(코드 확인: `services/public_api/intraday/*`, `api/local_intraday.py` 변경 없음).
- **확인 방법**: API를 `start_local_api.ps1`로 다시 시작하면 "Loaded from .env (값은 가려짐)" 목록에 각 키가 `set`/`missing`으로 출력된다. 이 출력으로 `.env`에서 변수가 올라갔는지 확정할 수 있다. 결과: 사용자 확인 대기(**미확인**).

## 7. 미해결 발견: F-5 Render 프록시 대역

API 로그에서 `PEER-DIAG`(첫 20건 진단)가 2건 확인됐다.

- 1/20: `peer=127.0.0.1`, `x-forwarded-for=None`, `path=/`
- 2/20: `peer=127.0.0.1`, `x-forwarded-for='34.82.93.227, 172.71.124.171, 10.26.34.133'`
- 헬스체크(`/api/v1/live`)는 별도 내부 주소(`10.237.25.91`)에서 들어옴(진단 대상 제외).

해석 후보(확정 아님): 앱이 직접 보는 접속 주소(peer)가 **루프백(127.0.0.1)** 이고, 실제 연결 경로는 `X-Forwarded-For` 목록에 담겨 있다. `34.82.93.227`, `172.71.124.171`, `10.26.34.133`이 각각 무엇인지는 확인하지 못했다. 이 구조에서는 "신뢰할 프록시 대역"을 무엇으로 두어야 안전한지 설계 판단이 필요하며, 20건이 모이기 전에는 결론을 내리지 않는다. **사용자가 실제 브라우저로 접속한 요청이 어떤 줄로 찍히는지**를 확인한 뒤, 절차서 §7과 `PUBLIC_API_TRUSTED_PROXY_IPS` 방식이 이 구조에 맞는지 다시 검토한다. 그 전에는 `REQUIRE_TRUSTED_PROXY=true`로 바꾸거나 대역을 입력하지 않는다.
