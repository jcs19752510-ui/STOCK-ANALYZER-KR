- 일자: 2026-10-06 / 기준 계약서: `docs/stock-detail/10-intraday-rescreen-contract.md`(§0·§3·§4·§7, DEC-090 `base_fill` 포함, 조율 중 추가된 `base_fill.pending`·`error.details` 반영) / 브랜치: `wt/frontend-livescreen`

- **백엔드 없이 가짜 JSON 서버로만 시험했다. 실제 백엔드·증권사 응답·실제 장중 데이터는 확인하지 못했다(§6).**
- 배포 필요: 없음(운영에서 꺼진 기능, DB 변경 없음). 푸시하면 Render가 자동 배포하지만 운영 화면은 달라지지 않는다.

- 동작 요점: 켜면 `/api/v1/local/screen*`을 일봉 화면과 **같은 조건 파라미터**로 부르고, 서버가 준 `meta.live.refresh_seconds`(5~60초 보정, 기본 10)마다 목록을 **제자리에서** 바꾼다(스켈레톤·재마운트 없음, 스크롤·현재 쪽 유지). 탭이 가려지면 멈추고 보이면 즉시. 실패 시 기본 간격에서 두 배씩(상한 30초) 재시도하며 마지막 값을 유지하고, 마지막 성공이 `refresh_seconds`의 3배를 넘으면 "지연" 배지. "일시정지"는 보이던 결과의 `snapshot_id`에 고정(쪽 이동도 같은 id), 410이면 고정을 풀고 한 번 새로 계산(일시정지·새 스냅샷 고정 유지, 안내 표시). "새로 계산"은 즉시 한 번. 같은 요청이 진행 중이면 합치고 다른 요청이 오면 이전 요청을 취소하며 늦은 응답은 버린다. "신규" 표지는 서버 `changes.entered`를 스냅샷마다 한 번만 반영해 약 60초(브라우저 시계로 잼), `changes.left`·`entered`는 "최근 변화"(최대 10건). 계산 경과(N초 전)는 응답 봉투의 서버 시각 기준이라 시계가 어긋나도 흔들리지 않는다. 켜짐은 localStorage에 기억(실패해도 이 탭에서는 동작).
- 낭독: 결과 영역의 기존 `aria-live=polite`는 켜진 동안 `off`, 건수 문구도 `off`. 대신 상태가 **바뀔 때만**(불러옴·일시정지/재개·지연/복구·오류·보충 시작·만료) 읽는 `role=status` 한 곳. 초 단위로 바뀌는 "N초 전"은 낭독 영역 밖.
- 켜진 동안 교체되는 안내: `liveQuoteNotice`("조건 판정은 일봉 기준…")·일봉 기준시각 배지(`DataFreshnessBadge`)는 배너로, 패턴의 "계산 기준: 종가·거래량 일봉 기준"은 장중 기준 문구로. 끄면 원래대로.
- **운영 번들 분리**: 요청·오류 코드·저장 키가 있는 모듈(`protocol.ts`·`controller.ts`)은 운영 빌드에서 쓰는 곳이 모두 제거되도록 `react.ts`의 같은 모듈 상수(`LIVE_BUILD`)로 감쌌다. 처음에는 `localIntraday.ts`의 공개 상수를 썼는데 번들에 코드가 남아(번들 검사 실패) 구조를 바꿨다(§5 결함 2).

2. (시험 중 발견, 제품) 운영 번들에 장중 기준 요청 경로·오류 코드·저장 키가 그대로 실림(요청은 0건이지만 코드가 남음) → 요청·응답 규칙(`protocol.ts`)과 표시 로직(`logic.ts`)을 분리하고 `react.ts` 안의 빌드 상수로 감싸 제거, 번들 검사로 확인(`snapshot_id`는 조건 정리 함수의 파라미터 이름으로만 남음, 요청 코드 아님). 켜짐 기억의 쓰기도 같은 상수로 감쌌다.
3. (설계상 사전 조치) 결과 영역의 `aria-live=polite`와 쪽 문구(`Pagination`)의 `aria-live=polite`가 10초마다 낭독될 수 있어 켜진 동안 `off`로 바꿈.
4. (시험 코드) 스냅샷 id를 응답 로그에서 읽어 화면이 고정한 것과 어긋나는 경합(5건) → 배너에 `data-snapshot-id`를 두고 화면에서 읽음. 가짜 서버의 `expireAll`이 직전 스냅샷 참조를 남겨 410이 되풀이되던 것 수정. 백오프 간격 측정의 시작 인덱스 오류 수정. 전체 화면 스크린샷이 너무 길어 보기 어려워 화면 영역 캡처로 변경. 끝 슬래시(`/screen/`)는 Next가 경로를 정리해 핸들러에 넘기므로(기존 `/screen/`도 동일) 브라우저 시험에서 빼고 `check-auth.mjs`의 정규식 시험으로 확인.

## 6. 확인하지 못한 것(가짜 서버·로컬 시험의 한계)
1. **실제 백엔드**: 응답 모양은 계약서만 보고 흉내 냈다. 실제 `meta.live` 필드·`changes`의 범위(§8-1)·`error.details`·`base_fill` 값의 의미·응답 시간·JSON 크기는 합친 뒤 종단 시험에서 확인해야 한다. 화면은 모양이 어긋난 응답(필수 필드 없음)을 성공으로 받아들이지 않고 오류로 표시한다.
2. **실제 증권사·장중 시세**: 시세 수신 비율·`stale`·일봉 보충 진행이 실제로 어떻게 움직이는지, 2,800종목 재계산이 `refresh_seconds` 안에 끝나는지, 장중에 "지연" 배지가 얼마나 자주 뜨는지는 알 수 없다.
3. **실제 PostgreSQL·DB 스택**: 사용하지 않았다(계약 §5의 동치·골든 시험은 백엔드 담당).
4. **스크린리더 실제 낭독**(NVDA·VoiceOver)은 듣지 못했다. `role=status` 영역의 내용 변화 횟수(15초 동안 ≤1)와 axe·구조만 확인했다. Chromium 하나만 사용(Safari·Firefox 없음). 모바일은 에뮬레이션 화면 폭(390·320)이며 실제 기기가 아니다.
5. **다크 테마**: 앱에 다크 테마(`prefers-color-scheme` 규칙)가 없어 `colorScheme: dark`로 찍어도 밝은 화면과 같다(스크린샷은 두 가지 모두 저장). 새 CSS는 기존 토큰만 써서 나중에 토큰이 바뀌면 따라간다. 고대비(forced-colors)와 모션 줄이기는 확인했다.
6. 수 시간 연속 열어 둔 상태의 메모리·누수, 실제 대량 `changes`(100건씩) 렌더 성능은 보지 않았다.
7. 로그인 켠 로컬에서 **쿠키가 5분 지나 API로 재확인하는 경로**(`apiSessionCheck`)는 시험하지 않았다(가짜 서버에 없음). 이 시험의 쿠키는 매번 새로 서명해 항상 "신선"하다.
8. 로그인을 끈 로컬에서 서버의 `require_owner`(IP 허용 등)가 거절하는 경우는 가짜 서버의 403으로만 확인했다(화면 안내·재시도 없음).

## 8. 계약서에서 모호하거나 이상해 보인 점 / 질문·미확정
1. **`changes`의 범위**: "이 페이지 조건 결과의 편입·이탈"이 (a) 조건 결과 전체인지 (b) 요청한 쪽의 항목만인지 불분명하다. 화면은 서버 값을 그대로 쓰되 **스냅샷마다 한 번만** 반영하고, 보이는 쪽에 있는 코드에만 "신규"를 붙이며 "최근 변화"에는 서버가 준 코드를 모두 보인다. (b)라면 쪽을 넘길 때마다 의미가 달라진다(같은 스냅샷이면 다시 반영하지 않음). 확정 필요.
2. **`excluded`와 `mismatched`의 관계**: `excluded`가 불일치로 뺀 종목을 포함하는지 불분명하다. 화면은 둘을 **각각 별도 문장**으로 보인다("N종목은 증권사 일봉 보충이 안 되어 결과에서 제외됨" / "증권사 일봉과 발행 일봉의 종가가 달라 계산에서 뺀 종목 N개"). 포함 관계가 확정되면 문구를 합칠 수 있다. 또 `pending`은 "N종목은 일봉 보충 중"으로 구분해 보인다(조율 메시지 반영).
3. **`base_fill.state:"failed"`**: 최종형은 none/running/ready뿐이지만 이전 초안의 `failed`도 받아들여 "보충에 실패했습니다" 안내를 한다(없으면 쓰이지 않음).
4. **조건 적용 중 일시정지**: 계약은 "조건 적용은 자동 갱신 요청을 새로 시작"이라고만 한다. 구현은 조건이 바뀌면 이전 결과를 비우고 `snapshot_id` 없이 새로 계산하며, 일시정지 상태였다면 일시정지는 유지하고 **새 결과의 스냅샷에 다시 고정**한다. 같은 조건으로 "조건 적용"을 다시 누르면 제자리 새로 계산이다.
5. **일시정지 중 "새로 계산"**: 고정을 풀고 새 스냅샷을 받아 거기에 다시 고정한다(요청 실패 시 이전 고정 유지). 서버 최소 계산 간격 안이면 서버가 직전 스냅샷을 줄 수 있어(계약상 강제 재계산 파라미터 없음) 같은 결과가 올 수 있다.
6. **다시 묻지 않는 오류**: `LIVE_BASE_STALE`(409)·400·401/403·404와 설정 문제 503(`FEATURE_DISABLED`·`LOCAL_INTRADAY_NOT_CONFIGURED` 등)은 자동 재시도하지 않고(탭 복귀로도 안 함) "다시 시도"·"일봉 기준으로 되돌리기" 버튼만 둔다. 이전 값은 지운다(믿을 수 없는 값을 남기지 않음). 그 밖의 503(`SERVICE_UNAVAILABLE` 등 일시 장애)·429·5xx·연결 실패는 백오프 재시도. 계약에 503의 세부 구분이 없어 정한 것이므로 확인 필요. `LIVE_BASE_FILLING`·`LIVE_QUOTES_NOT_READY`는 5초 고정 간격(실패 횟수에 넣지 않음).
7. **"지연" 판정**: "마지막 성공 > 3×refresh_seconds"(경계 포함 안 함)일 때 배지. 일시정지 중에는 의도된 고정이라 지연으로 보지 않는다. 최근 실패는 배지와 별도로 "최근 갱신에 실패해 마지막 값을 보여 줍니다" 안내를 즉시 보인다.
8. **켜짐 기억**: 두 화면이 **같은 키**(`stock.liveScreen.on`)를 공유한다(한쪽에서 켜면 다른 쪽도 켜짐). 화면마다 따로 기억해야 하면 알려 달라.
9. **관리자 확인**: `localIntradayAvailable()`은 역할을 모른다. 로그인을 켠 로컬 빌드에서는 `/auth/me`(기존 머리글 메뉴와 같은 경로)의 `role=admin`일 때만 전환을 보이고, 로그인을 끈 로컬은 내 PC 본인으로 보고 보인다(서버가 403이면 오류 안내). 일반 회원에게는 전환도 `/local/screen` 요청도 없다(시험 A022~A025).
10. 계약 §4의 "시세 수신 covered/total종목"의 분모는 `quotes_total`(활성 종목 수)이며 화면의 결과 건수와 다르다 — 의도대로 표시한다.
11. 계약 §3의 `refresh_seconds`가 서버 최소 계산 간격보다 짧으면 같은 스냅샷이 반복될 수 있다. 화면은 `changes`를 중복 반영하지 않는다.

## 9. 위험
- 서버가 `refresh_seconds`를 크게(60초) 주면 값이 최대 1분 묵는다. 화면은 "N초 전"을 항상 보이며 3배(3분)를 넘기면 "지연"으로 표시한다.
- 켜진 동안 시세 열(`useQuotes`→`liveMarket`)은 별도 주기로 조회한다. 결과 코드가 바뀌면 기존 구현대로 현재가가 잠깐 "-"가 될 수 있다(DEC-088 결과서 요청 2와 동일, 이번에 고치지 않음). 장중 기준 값과 현재가 열은 서로 다른 시각의 값일 수 있어, 배너가 계산 시각을 따로 알린다.
- 응답이 느리면(계산 수 초) 쪽 이동은 응답이 올 때까지 이전 쪽이 보인다("계산 중" 표시). 취소된 요청의 늦은 응답은 버린다.
- 일시정지 중에는 서버가 스냅샷을 최근 5개만 보관하므로, 오래 두면 쪽 이동 때 410이 나고 새로 계산한다(안내 표시).

## 10. DEC-089 화면 쪽 메모(이 문서에만 적음 — decisions.md·HANDOFF.md는 메인이 편집)
- 상태: **화면·웹 서버 대행 허용 경로는 구현·가짜 서버 시험 완료, 실제 백엔드와의 종단 시험은 합친 뒤 필요.** 접근은 로컬 모드 관리자 한정(DEC-085 연장), 운영 빌드에는 코드·요청이 번들에서도 제거됨(번들 검사).
- 합칠 때 확인할 것: (1) `meta.live`·`error.details`·`changes`·`base_fill.pending`의 실제 값 (2) 실제 서버 최소 계산 간격과 `refresh_seconds` (3) `LIVE_BASE_STALE` 문구에 날짜가 들어가는 점(화면은 서버 문구를 "서버 안내"로 그대로 보임) (4) 위 §8의 질문 항목.
- 복원 방법: 화면에서 "일봉 기준으로 되돌리기" 또는 스위치 끄기. 코드 롤백은 `ScreenerClient`·`PatternScreenerClient`의 장중 기준 연결을 제거하면 된다.
