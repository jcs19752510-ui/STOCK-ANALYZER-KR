## 4. 핵심 시험 항목(요지)
- **가입**: 승인 대기·일반 권한·비활성으로만 생성, 해시 저장, 승인 전 로그인은 본인(비밀번호 맞음)에게만 "승인 대기" 안내(틀리면 평범한 실패), 세션 미생성, 약한 비밀번호·형식 오류·중복(대소문자 무관) 거부, `role/is_active/approved_at` 주입 무시, 교차 사이트 403, 봇 칸 채움은 성공처럼 응답하나 미생성, 신청 제한 429·대기 상한 503.
- **관리자**: 승인→로그인 가능, 거절=삭제, 회원 추가(약한 비밀번호·중복 거부), 이름 수정, 비밀번호 초기화(정책 검사·잠금 해제·기존 세션 취소), 권한 변경, 사용 중지(로그인 중 세션 즉시 취소·재사용해도 부활 없음), 모든 기기 로그아웃, 삭제(세션 연쇄 삭제).
- **권한 확인의 위치**: 일반 사용자의 관리 화면 접근은 홈으로, 관리 작업·투자자 값 호출은 403. **강등된 사용자의 옛 쿠키(rl=a)로도 서버가 즉시 403**, 쿠키 표시는 5분 확인 때 갱신. 브라우저가 보낸 위조 헤더 무시.
- **보호 규칙**: 본인 비활성화·삭제·강등(우회 호출 포함) 409, 두 관리자가 동시에 서로를 제거해도 관리자 0명이 되지 않음.
- **감사**: 관리 작업이 기록되고 비밀번호·해시는 기록되지 않음, 행위자 삭제 후에도 기록 보존.
- **화면**: 가입·관리자 화면 360/1280px 가로 넘침 없음, axe 위반 0, 입력칸·버튼 44px 이상, 이름의 `<script>`는 글자로만 표시. 캡처: `docs/qa/2026-10-05/signup-360.png`, `admin-members-360.png`, `admin-members-1280.png`, `admin-members-after-1280.png`.

## 5. 시험 중 발견·수정한 결함 (정직한 기록)
1. **로그인 폼 버그**: 승인 대기·사용 중지 안내가 항상 "입력을 확인해 주세요"로 나왔다(이미 읽은 응답 본문을 다시 읽으려 함) → 파싱한 본문의 코드를 쓰도록 수정, E2E로 확인.
2. **`/admin/actions` 비로그인 요청이 401이 아니라 로그인 화면으로 이동** → 프록시가 이 경로를 API형(JSON 401)으로 처리하도록 수정.
3. **시험 설계 오류 3건**: 스트리밍 화면 로딩 전에 읽음, 이전 안내 문구를 읽음, 같은 접속 주소(가짜 IP)를 서로 다른 시험이 공유해 429 위치가 어긋남 → 시험을 고쳐 원인과 무관한 통과/실패를 제거.
4. 초기 관리자 표 모양: 작업 열이 좁아 버튼이 세로로 길게 쌓임·잘림 → 열 폭과 줄바꿈 조정(캡처로 확인).

## 6. 알려진 한계 / 미확인
1. 이메일 인증·CAPTCHA가 없다. 가입 신청 폭주는 제한과 대기 상한, **관리자 승인이 최종 관문**이다. 접속 주소를 알 수 없는 설정(`FRONTEND_TRUSTED_PROXY_HOPS=0`)에서는 모든 신청이 한 묶음으로 집계된다.
2. 권한 변경·사용 중지는 서버에 즉시 기록되고 API는 즉시 적용하지만, **웹 화면의 권한 표시(쿠키)와 이미 복사된 쿠키는 최대 5분** 늦게 반영된다.
3. 관리자 작업 기록은 CLI(`manage_users.py admin-audit`)로만 조회한다(화면 없음).
4. 증권사(KIS) 시세를 관리자 외 사람에게 보이는 것의 약관 해당 여부는 확인하지 않았다(관리자 화면에서 관리자로 올리면 볼 수 있음).
5. **Render·Neon·KIS 실서버, 실기기, 실제 브라우저 비밀번호 저장 창은 확인하지 못했다.** 운영의 기존 DB(0017 적용 상태)에서 0018을 적용하는 과정은 임시 DB의 "0017→0018 이전 시험"으로만 확인했다.
6. AI는 운영 배포·Neon 변경을 하지 않았다.

## 7. 운영 첫 적용 중 발견·수정 (2026-10-05, 실서버)
- **증상**: 운영에서 로그인 화면은 뜨는데 올바른 비밀번호로도 "아이디 또는 비밀번호가 올바르지 않습니다". `manage_users.py audit`에 **로그인 기록이 0건**이었다(비밀번호가 틀려도 기록은 남아야 한다 → 요청이 로그인 확인에 도달하지 못함).
- **원인**: 웹의 내부 토큰(새 값)과 API의 내부 토큰(옛 값)이 달라 API가 `401 AUTH_REQUIRED`를 돌려줬고, 웹이 **모든 401을 "비밀번호 오류"로 표시**했다. 토큰이 달라진 것은 절차 안내("이미 있는 값은 그대로 두고 없는 것만 추가")가 API의 기존 토큰을 새 값으로 바꾸지 못하게 한 **안내 오류**였다.
- **수정**: ① 웹: 401은 오류 코드가 `INVALID_CREDENTIALS`일 때만 비밀번호 오류로 표시하고, 그 밖(토큰 불일치 등)은 "서버에 연결하지 못했습니다"로 표시(`loginFailure.ts`, 단위 시험 2건 추가: 프런트 29건 통과, 로그인 화면 E2E 20건 통과). ② 절차: API의 `PUBLIC_API_INTERNAL_TOKEN`을 **웹과 같은 새 값으로 수정**하도록 안내.
- **교훈**: 설정 오류가 사용자에게 인증 실패로 보이면 원인 파악이 늦어진다 → 실패 원인을 구분해 표시. 실서버 기록(`audit`)이 원인 판별에 결정적이었다.

### 7-1. 재발 방지: 운영 설정 오류를 재현하는 시험과 점검 주소 (추가)
- **내부 시험 공백(인정)**: 지금까지의 시험은 웹과 API에 같은 토큰을 넣은 환경에서만 했다. 서버 간 설정이 어긋난 운영 상황은 시험하지 않았고, 그래서 운영에서 처음 드러났다.
- **추가 시험**: E2E 하네스가 **내부 토큰이 API와 다른 웹**을 별도로 띄워(운영의 실제 오류 재현) 확인한다 — 올바른 비밀번호로 로그인해도 "비밀번호 오류"가 아니라 "서버에 연결하지 못했습니다"가 표시되고, 쿠키가 만들어지지 않으며, DB 로그인 기록이 늘지 않음(운영에서 원인을 가른 단서와 동일).
- **점검 주소 `GET /auth/status`**: 로그인 없이 열 수 있고 상태 이름만 알린다(값·비밀 없음). `api`: `ok` / `token_mismatch`(내부 토큰 불일치) / `auth_not_configured`(회원 DB 설정 없음) / `unreachable`(API 연결 불가). 정상 설정에서 200, 토큰 불일치에서 503으로 시험.
- 결과: E2E 전체 **322 중 322 통과**(섹션 M 신규 5건 포함), 프런트 단위 118건 통과, tsc·eslint 오류 0.

### 7-2. 운영 로그인 실패 추가 분석 (API 직접 호출)
- 운영 API를 직접 호출(`POST /api/v1/internal/auth/login`, 내부 토큰 포함)한 결과 `401 INVALID_CREDENTIALS` → **내부 토큰·API·DB 접속은 정상이고, 저장된 비밀번호 해시와 입력값이 불일치**.
- **의심 원인**: Windows PowerShell이 `"비밀번호" | … --password-stdin`으로 보낼 때 맨 앞에 붙일 수 있는 보이지 않는 BOM(U+FEFF). 붙은 채 해시되면 화면에서 같은 비밀번호를 입력해도 불일치한다.
- **수정**: 관리 스크립트가 표준입력 비밀번호의 BOM을 제거(시험: BOM이 붙은 입력으로 등록해도 BOM 없는 비밀번호로 로그인되는 해시가 저장됨). **점검 명령 `manage_users.py verify-password <아이디>` 추가**(입력한 비밀번호가 저장된 값과 맞는지만 출력, 값은 출력하지 않음). 통합 시험 43건 통과.
- 상태: §7-3에서 실서버로 확정(아래).

**내부 시험의 공백(정직한 기록)**: 코드 시험은 웹·API에 같은 토큰을 넣은 환경에서만 했고, ① Render 환경변수의 일치 여부 ② 자동 배포 연결 값(GitHub Secrets) 등록 여부는 시험 대상이 아니었다. 이후 재발 방지로 배포 후 점검(`/auth/status` 200 확인)을 배포 절차에 포함해야 한다(미반영, 할 일).

## 8. 로컬 서버(내 PC) 로그인 적용 (DEC-075)
- 사용자 결정: 로컬 회원 DB=운영 Neon 회원 DB 공유 / 로컬 로그인=기본 켬 + 끄는 스위치 / 첫 관리자=Neon의 `jcs1973`. 요구: "로컬에서만 정상 동작하던 부분(호가·체결·분봉 등)은 그대로".
- 핵심 설계 문제: 로그인을 켜면 API가 토큰 없는 브라우저 직접 호출을 거부 → 개인 로컬 모드(브라우저가 4001을 직접 호출)가 깨진다. 해결: 웹 서버 대행 경로가 `NEXT_PUBLIC_LOCAL_INTRADAY_ENABLED=true`로 빌드한 웹에서만 `/api/v1/local/*`(status·minutes·ticks·orderbook·investor)를 대행하고, 로컬 투자자 수급은 관리자만(일반 403). 운영 빌드는 그 값이 없어 계속 404.

### 8-4. 알려진 한계 / 미확인 (정직한 기록)
- **Windows PC에서 직접 실행하지 못했다**(시험은 리눅스 임시 환경). PowerShell 스크립트(`start_local_api.ps1`)는 키 목록만 수정했고 실행은 못 했다. 윈도우 파일 특성(CRLF·BOM)은 단위 시험으로 재현했다.
- 로컬이 **운영 Neon 회원 DB에 실제로 붙는 경로**는 시험하지 못했다(시험은 임시 PostgreSQL을 회원 DB로 사용). 접속 확인 단계(`[확인] 회원 DB 접속 확인`)가 사용자 PC에서 이를 알려준다.
- 로컬 로그인을 켜면 로컬 API의 Swagger(`/docs`)와 토큰 없는 `curl`이 닫힌다(운영과 같은 동작, 끄기로 복구).
- 로컬과 운영이 회원 DB를 공유하므로 로컬 관리 작업이 운영 회원에 즉시 반영된다.
- 운영 로그인 문제(§7-3)는 별개로 아직 열려 있다.

## 10. 운영 로그인 재확인과 "서버에 연결하지 못했습니다" 수정 (DEC-077, 2026-10-06 오전)
- **운영 상태 재확인(실서버 직접 조회)**: 웹을 최신 코드로 재배포한 뒤 `/auth/status`가 `{"ok":true,"web":"ok","api":"ok"}`(200)로 확인됨 → **웹·API 내부 토큰은 일치**(§7-3의 "토큰 불일치" 판단은 이 시점에 해소됨). `jcs1973`·`jcw1973`(사용자가 관리자 화면에서 추가한 관리자 계정) 로그인 `SUCCESS` 기록, 직접 재전송한 로그인 요청도 200. 회원은 jcs1973(관리자)·jcs1975(관리자)·jcw1973(관리자). 점검용 계정은 삭제된 상태.
- **재현·원인**: 사용자 화면에 "서버에 연결하지 못했습니다"가 표시된 직후 같은 요청이 성공 → 무료 호스팅 API가 유휴 후 깨어나는 동안의 일시적 실패. 로그인 호출만 재시도가 없었다.
- **수정**: 로그인이 일시적 실패(연결 오류·502/503/504)를 최대 3회(대기 3·6초) 재시도. 401(비밀번호 오류·토큰 불일치)·429는 재시도 안 함.
