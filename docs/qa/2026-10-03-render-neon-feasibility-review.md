# Render(웹/API) + Neon(DB) 전환 타당성 검토 및 내부시험 결과서

- 작성일: 2026-10-03 (KST) / 브랜치 `PROD_SCH` / 요청: 사용자 — "Oracle이 안 되면 Render 서버와 NeonDB로 바꿔도 되는지, DB 파일이 200MB도 안 되는 것 같으니 검토해 달라"
- 성격: **전환 가능성 검토**(배포 파일은 바꾸지 않았다). 결정은 사용자 몫이다.
- **한계(먼저 읽어 주세요)**: 개발 환경에서 Render·Neon에 접속할 수 없어(네트워크 차단) **실제 Render/Neon 위에서의 시험은 하지 못했다.** 아래 "시험함"은 Neon과 **같은 조건**(SSL 필수, SCRAM 비밀번호 인증, 채널 바인딩, 연결 끊김)을 임시 PostgreSQL 16에 만들어 우리 코드를 돌린 결과이고, 요금·한도는 **웹 검색 결과**(공식 페이지 직접 확인 불가)다.

## 1. 결론
| 질문 | 답 |
|---|---|
| DB가 200MB도 안 되는데 Neon 무료에 들어가나? | **지금은 들어간다.** 현재 163MB. 한도는 검색 결과 대부분 **0.5GB**(2026-10-01에 1GB로 늘었다는 출처 1건은 재확인 못 함). 증가 속도 추정(월 35~45MB)이면 0.5GB는 약 8~10개월, 1GB면 약 18~22개월 후 도달 |
| Render + Neon으로 **지금 구성 그대로** 옮길 수 있나? | **아니다.** 설계 변경이 필요한 항목 5개가 있다(§3). 가장 큰 것은 ① 무료 플랜에는 **스케줄 배치(cron)가 없음**, ② **15분 유휴 시 절전(깨우는 데 약 1분)**, ③ **프록시 뒤에서 방문자 제한(분당 60회)이 전 방문자 공용이 되는 문제(시험으로 확인)** |
| 그래도 가능한가? | **베타(소수 사용자)용으로는 가능, 정식 서비스용으로는 비권장.** 서버를 구할 수 없고 반드시 0원이어야 할 때의 임시안으로 본다 |
| 권장 순서 | ① Oracle 지원 답변(10/8까지) → ② 국내·해외 VPS(4GB급 월 $20 안팎, 현재 구성 거의 그대로) → ③ Render+Neon 무료(베타 임시안) |

## 2. 현재 데이터 규모 (사용자 PC 실측)
DB 163MB, `raw_ohlcv` 370,940행, `daily_prices` 370,940행, 지표 24,855행, 실적 7,751행(약 130거래일 × 2,766종목). 덤프 파일 18.8MB.
- 증가 추정(±40%): 시세 두 테이블이 한 해에 각 약 69만 행, 지표 포함 연 400~500MB. **추정이며 정확한 값은 6개월 뒤 다시 측정해야 한다.**
- 용량을 지키려면 공개용 일봉 사본·지표의 **보관 기간 제한**(예: 250거래일)이 필요하다(설계 변경, 사용자 결정 사항).

## 4. 시험 결과 (임시 PostgreSQL 16, SSL·SCRAM 켬)
| ID | 시험 | 결과 |
|---|---|---|
| T1 | Neon 방식 연결 문자열(`?sslmode=require&channel_binding=require`)로 Alembic 마이그레이션 0001→0014 | **성공**, 버전 0014 |
| T1-a | 비밀번호가 틀리면 TCP 접속 거부, 접속은 SSL 사용(`ssl=true`) | 확인 |
| T1-b | SSL 파라미터 없는 기존 URL도 동작(기본 `prefer`) / `verify-full`은 루트 인증서가 없으면 명확한 오류 | 확인 |
| T2 | 같은 연결 문자열로 공개 API 기동 → `/api/v1/health` | `status ok, db ok` |
| T3 | 서버가 연결을 모두 끊은 직후(컴퓨트 정지·재시작과 같은 상황) 요청 3회 | **모두 HTTP 200, 약 15ms**(`pool_pre_ping` 덕분) |
| T4 | DB를 완전히 내렸다가 다시 올림 | 내려가 있는 동안 **503, 0.02초**(`/health`는 `db: degraded`), 올라온 뒤 **즉시 200** |
| T4-a | 한계: 연결 시간 제한이 **3초**(`connect_timeout`)라서 Neon이 깨어나는 데 3초가 넘으면 **첫 방문자가 503**을 받을 수 있음 | **코드 읽기로 확인**(재개 지연 자체는 시험 불가) |
| T5 | API 메모리·시작 | 60회 요청 후 **약 90MB**, 시작 후 첫 응답까지 **0.78초** |
| T6 | Next.js 프로덕션 | 빌드 17초, **피크 약 1.2GB(빌드 단계 전체)**, 실행 시 **next-server 97MB → 80회 요청 후 132MB**, 시작 후 첫 응답 1.0초, 로컬 응답 6~32ms |
| T7-1 | 프록시를 **신뢰하지 않을 때**: 서로 다른 방문자 70명이 프록시 1대를 통해 호출 | **59명 통과, 11명 차단(429)** → 전 방문자가 분당 60회를 공유 |
| T7-2 | 프록시 IP를 신뢰(현재 compose 방식) | 70/70 통과 |
| T7-3 | 프록시를 **IP 대역(CIDR)** 으로 신뢰 | 70/70 통과(대역 지정 가능) |
| T7-4 | 신뢰 대상을 `*`(전부)로 | 70/70 통과, **한 대의 기기가 가짜 방문자 IP를 바꿔 120회 호출해도 차단 0건 → 제한 우회 가능(보안 결함)** |
| T8 | Neon 풀러(PgBouncer) 사용, 실제 Neon/Render 접속, 해외 IP에서 공공데이터·DART 호출, 싱가포르 지연 | **시험하지 못함**(개발 환경 접속 차단) |

## 5. Neon 풀러에 대한 주의 (확인하지 못함, 검색 근거)
- Neon은 PgBouncer 트랜잭션 모드를 쓰며 프로토콜 수준 준비된 문장은 지원한다고 한다.
- 우리 API는 연결 때 `options=-c statement_timeout=3000`(시작 매개변수)을 보낸다. **PgBouncer는 이런 시작 매개변수를 거부하는 일반적 제약**이 있어 풀러 주소로는 오류가 날 수 있다(Neon 공식 문서로 확인하지 못함). **직접 연결(unpooled) 주소를 쓰는 것을 권한다.** 무료 컴퓨트의 동시 연결 한도는 이 프로젝트의 풀 크기(최대 15)에 충분할 것으로 본다(미확인).

## 8. 전환하기로 결정할 경우의 작업 범위(예상 1~2일 + 실제 Render/Neon 시험)
1. 배치·백업·점검을 GitHub Actions 예약 실행으로 이전(Secrets 등록, 지연·해외 IP 확인).
2. 프록시 신뢰 IP 대역 확인 후 `PUBLIC_API_TRUSTED_PROXY_IPS`에 CIDR 설정, 확인 못 하면 중단.
3. DB 연결: 직접 연결 주소, `sslmode=require`, 첫 요청 지연을 고려한 `connect_timeout` 조정.
4. 헬스체크 경로를 DB 비조회로 분리.
5. 보관 기간 제한(예: 250거래일) 설계·구현·시험(사용자 결정).
6. Render용 배포 절차서·시험 결과서 작성, 절전 상태 안내 문구(첫 방문 지연) 추가.

## 9. 미확인 목록
- 실제 Render/Neon에서의 동작·속도·절전 재개 시간, 0.1 CPU 응답 시간
- Render 프록시 IP 대역, Neon 풀러의 `options` 처리, 컴퓨트 재개가 3초를 넘는지
- Neon 무료 저장 한도(0.5GB 대 1GB), 컴퓨트 시간(100 대 191.9) — **출처가 서로 다름**
- 해외 IP에서 공공데이터포털·DART·KIS 호출 가능 여부
- GitHub Actions 예약 배치의 실제 소요 시간(분)과 월 한도 여유
